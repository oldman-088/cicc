# PostgreSQL role-bound tenant isolation — experimental proposal

## Threat model and alternatives
The earlier transaction-local `cicc.tenant_id` policy (still preserved) stops accidental missing filters but **cannot** stop arbitrary SQL under the app role from selecting a different tenant. `PostgresRelationshipStore(..., tenant_binding='session_role')` and `schema/p2_01_role_bound_rls_proposal.sql` explore a stronger *optional, isolated proposal*: a separate authenticated PostgreSQL login per tenant, a protected administrator-owned mapping from PostgreSQL `session_user` to one tenant, and FORCE RLS using only that mapping. An untrusted tenant field and mutable GUC do not set the DB identity. No shared schema, role, or migration was changed.

## Mechanics and prerequisite controls
1. Apply `p2_01_postgres_proposal.sql`, `p2_01_rls_proposal.sql`, and the role-bound proposal in order **only** in an approved isolated environment. The final proposal creates restricted schema `ti_security`, mapping table and `SECURITY DEFINER` lookup function with fixed `search_path = pg_catalog` and fully qualified mapping reference, revokes PUBLIC access, and replaces the four GUC policies. The mapping's login name is the PostgreSQL-authenticated `session_user`, not `current_user` or the HTTP request. A missing mapping returns NULL and is denied by RLS.
2. An administrator must create distinct login roles and provision their mappings. Grant only required table operations and sequence access plus `USAGE` on `ti_security` and `EXECUTE` on the lookup to appropriate tenant runtime roles. Runtime must not own tables, mapping, function or schema; must lack CREATE on trusted/search-path schemas, BYPASSRLS, superuser, DDL, membership or `SET ROLE` to other tenant roles, and must not be able to modify role memberships or authenticate as another tenant login. Safeguard credentials and principal-to-pool selection. Do not use a shared server-side login for all tenants: `session_user` must reflect the actual tenant login, including with poolers/proxies. Session login identity must not be switchable via `SET SESSION AUTHORIZATION`; non-superuser tests verify this.
3. Host authenticates an end user, derives tenant and permissions from an approved trusted identity source, selects that tenant login's connection pool, and supplies `AuditContext`. The store compares host tenant to lookup, checks both session/current role are not superuser/BYPASSRLS, checks FORCE RLS and matches the expected policy names/expressions with no extra policies; failures abort. These checks do **not** verify function body/ownership, grants, role membership graph, object resolution or role credential security. Exact `pg_get_expr` matching is intentionally fail-closed but version-sensitive; deployment must validate supported PostgreSQL versions. Secure database search path and prevent shadowing objects.

## Tested and residual risks
Isolated local PostgreSQL tests use two distinct non-superuser/non-BYPASSRLS logins. Arbitrary tenant GUC changes and SET ROLE to a common inherited role did not permit cross-tenant record/audit reads or inserts. Cross-tenant UPDATE/DELETE were filtered even with temporarily granted privileges; direct access to mapping, changing policies and switching to another login were denied. Pool reuse, rollback, cross-tenant concurrent reads, an extra permissive policy, role mismatch and transactional audit failure were tested. The alternate rollback proposal was run and re-applied on the disposable DB; the role-bound store detected the wrong policy and failed closed. This is a local test of a proposed model, **not production isolation or host integration**.

Database owner, superuser, BYPASSRLS role, compromised role membership, mutable trusted schema/function/mapping, a stolen other-tenant credential, direct access to administrative login, or a pooler using a shared server login can defeat the model. A tenant login with arbitrary SQL can read/write its **own** tenant data as granted, bypass application-level permissions, and can forge its own tenant audit rows if granted audit INSERT; this is demonstrated by an explicit test. Transactional audit rollback does not make the audit tamper-proof. A controlled database-side entry point or separate append-only audit service/role is still needed for stronger in-tenant authorization and trustworthy actor attribution. Platform auth/tenant mapping, least privilege, audit policy, host-approved migrations and threat model require owner approval and real-host verification. Record provenance is not proof of authenticity.

## Rollback
`p2_01_role_bound_rls_rollback_proposal.sql` restores the old mutable-GUC policies without dropping mapping/function data; it is a **security downgrade**. The role-bound store refuses operations after this policy change. Deploy only after owner approval, a safe maintenance plan, backups, and independently verified compensating tenant controls. No rollback was run against shared infrastructure. The existing separate base RLS rollback likewise removes tenant controls and is not safe by default.
