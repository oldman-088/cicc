# API

FastAPI exposes OpenAPI at `/docs`. `GET /health` reports synthetic-demo and production readiness false. `GET /api/v1/overview` returns synthetic records, a notice and planned source statuses. Both are unauthenticated, read-only, and unsuitable for sensitive data. No tenant, real source or mutation APIs exist. Confidence values are synthetic examples, not assertions of certainty.

## Experimental, opt-in authenticated routes

Disabled by default; configuration and security limitations in README and SECURITY_STATUS.md. HTTPS required at ASGI scope. `POST /api/v1/secure/login` takes tenant_id, username, password and returns an opaque bearer token and eight-hour expiry; invalid credentials return 401 and throttling returns 429. `POST /api/v1/secure/logout` revokes the bearer token. `GET /api/v1/secure/entities` requires a bearer token, derives tenant from it, audits the read, returns at most 100 records and indicates `truncated`; pass `next_cursor` as `after` to read the next page. Invalid/expired/revoked tokens return 401. Selected routes have been tested on disposable PostgreSQL 16.2 with simulated HTTPS, but not under real TLS and are not connected to the web UI. Administrator-only experimental account endpoints: `POST /api/v1/secure/users` creates a user from username, password and role; `PATCH /api/v1/secure/users/{id}/role` changes a role; `POST /api/v1/secure/users/{id}/disable` disables the user and revokes sessions. All derive tenant from the administrator session, deny cross-tenant and self role/disable actions, and audit mutations. Invalid sessions return 401, authorization failures return 403 and duplicate creation returns 409.

### Experimental manual intelligence

`POST /api/v1/secure/entities` requires an analyst or admin bearer token and accepts `kind` (indicator, vulnerability, threat_actor, campaign, asset, incident, report, other), `title`, `source`, optional `source_reference`, and optional integer `confidence` 0–100. The server assigns the session tenant and creator, records an audit event, and sets verification to `unverified`. Confidence is an analyst-supplied assessment, not fact or calculated certainty. Source references are stored as text and never fetched. `GET /api/v1/secure/entities` returns these fields in pages of up to 100 using the optional `after` cursor and `next_cursor`. This is a minimal experimental creation path, not a complete intelligence lifecycle: evidence, updates, deduplication, history and connector provenance are not implemented. Do not use real data until security and PostgreSQL are validated.

### Evidence references (experimental)

`POST /api/v1/secure/entities/{id}/evidence` accepts an analyst-entered description and source, optional inert reference and optional lowercase SHA-256 string. Analysts/admins may create; all authorized intelligence readers may use `GET` on the same path. References are tenant-scoped, audit events are recorded, pages contain at most 100 results with truncation indicated, and records are labeled `analyst_entered_unverified`. No file is uploaded, retrieved, scanned, hashed or verified; a supplied digest is merely an assertion. No edit/delete, chain of custody or complete evidence lifecycle exists.

### Experimental provenance history

`GET /api/v1/secure/entities/{id}/provenance` requires an authorized bearer session and tenant-scopes and audits the read. It returns at most 100 ordered events per page and signals truncation. New manual entity creations and evidence-reference additions record actor, timestamp, event type and a limited source snapshot in the same transaction as the write. History before this feature was introduced is not backfilled; an empty list is not proof that nothing happened. The API does not expose edits or deletion of events, but database-level immutability and full provenance are not implemented. Evidence digests and references remain unverified.

### Experimental audit access

`GET /api/v1/secure/audit` requires an administrator bearer session and returns up to 100 events for that session's tenant, newest first. Use `next_cursor` as `before` for the next page; cursors must reference an event in the current tenant. Each access is audited and the new audit-read event appears on a subsequent fresh read. This traversal is not a consistent snapshot. Export, tamper resistance and retention are not implemented. The event stream is incomplete for unknown tenants and offline operator attribution.

### Experimental entity updates

`PATCH /api/v1/secure/entities/{id}` requires analyst/admin and `expected_version`, `title`, and `confidence` (integer 0–100 or null). The tenant comes from the session; stale versions return 409 and other-tenant IDs return 404. Successful edits increment version, reset verification to unverified, and atomically record before/after provenance and audit. Source, type and evidence cannot be changed through this endpoint. This is not a complete lifecycle or verification workflow.

Experimental `/api/v1/secure` request bodies are limited to 16 KiB, including streamed bodies; oversized requests return 413. A trusted reverse proxy should enforce its own limits and timeouts as well.

### Experimental relationship assertions

`POST /api/v1/secure/relationships` allows an analyst/admin to assert a relationship between two distinct entities in the session's tenant. Inputs: `subject_id`, `object_id`, one of the documented relationship kinds in OpenAPI, `source`, optional `confidence` (0–100) and optional `evidence_id` tied to the subject entity. Every created relationship is labeled `analyst_assertion_unverified`; evidence references and confidence are not independently verified. `GET /api/v1/secure/entities/{id}/relationships` shows inbound and outbound relations, up to 100 per page with truncation. Both operations are audited; creation records provenance on the subject. No automated correlation, evidence validation, edits, deletion or visualization is implemented.

### Experimental source status and recovery

Administrators may use `GET /api/v1/secure/sources/cisa-kev/status` to inspect the tenant's last recorded attempt and last imported snapshot timestamp. `POST /api/v1/secure/sources/cisa-kev/attempts/{attempt_id}/abandon` marks a running attempt abandoned. Both require an authenticated administrator and are audited. Abandonment prevents a late import but does not terminate an already running network operation. The API has no start-sync endpoint, scheduler or verified live connection; a null attempt means none was recorded, not a healthy connection. Status is labeled experimental and not live verified.

Entity pagination orders by UUID and is not a snapshot: records inserted or deleted during traversal may not appear in the current walk. Each page is separately authorized and audited; do not interpret an empty page as evidence that no historical intelligence exists.

Evidence, provenance and relationship listings return `next_cursor`; pass it as `after` to retrieve the next page. Evidence is ordered by UUID; provenance and relationships are ordered by timestamp then UUID and require their cursor to identify a record in the requested entity and tenant. Every page is separately authorized and audited. Traversals are not consistent snapshots; concurrent inserts or deletes can be missed.

### Experimental investigations
`POST /api/v1/secure/investigations` creates a case with `title` and `description` for an analyst/admin; it starts `open` at version 1. `GET /api/v1/secure/investigations` lists the current tenant's cases, up to 100 per page, with `next_cursor` passed as `after`. `PATCH /api/v1/secure/investigations/{id}/status` requires analyst/admin, `status` (`open` or `closed`) and `expected_version`; stale versions return 409. `GET /api/v1/secure/investigations/{id}/events` returns case history in chronological pages, using `next_cursor` as `after`. Reads require a valid authorized session; cross-tenant IDs return 404. Creation/status events and case-specific security audit are transactional; case event reads also audit the case ID, while case-list reads have no single target. Older audit records were not backfilled; case history identifies changes but is not tamper-resistant. Pagination is not a consistent snapshot. This foundation has no file uploads, chain of custody, reports, case deletion or UI. Do not use for sensitive or operational data.

Analysts/admins can associate an existing same-tenant entity with an open case using `POST /api/v1/secure/investigations/{id}/entities` with `entity_id`. Duplicate or closed-case links return 409; foreign IDs return 404. `GET` on the same path lists links in UUID pages using `next_cursor` as `after`. Links are analyst associations, explicitly unverified and not evidence of involvement. Analysts/admins may unlink from an open case after removing its evidence associations using `DELETE /api/v1/secure/investigations/{id}/entities/{link_id}`; missing or cross-tenant IDs return 404 and closed cases return 409. Unlink preserves case history and audit but removes the current link, and a later relink creates a new ID. The link, case event, and audit with both case and entity targets commit atomically. Pagination is not a consistent snapshot.

An analyst/admin can link an existing evidence reference to an open case via `POST /api/v1/secure/investigations/{id}/evidence` with `entity_id` and `evidence_id`. The entity must already be linked to the case and the reference must belong to that entity and tenant; duplicates return 409, mismatched or foreign identifiers return 404. Readers may `GET` this path with UUID pagination (`next_cursor` as `after`); analysts/admins may unlink via `DELETE /api/v1/secure/investigations/{id}/evidence/{link_id}` while the case is open. An entity association cannot be removed until its evidence associations are unlinked. History and audit are transactional. These are unverified analyst-entered references: no file is retrieved, uploaded, hashed or validated, and this is not a chain of custody.

Administrators can set or clear an open case's assignee using `PATCH /api/v1/secure/investigations/{id}/assignment` with `assignee_id` (UUID or null) and `expected_version`. Only active analysts/admins in the case tenant are eligible at assignment time; stale versions or closed cases return 409, and invalid/foreign/ineligible assignees return 404. The operation records case history and targeted audit atomically. Disabling or demoting an assignee later does not automatically clear assignments; operators must review and reassign them. Assignment does not grant additional access.

Case listing exposes `assignee_status`: `unassigned`, `eligible`, or `ineligible` based on the account state at the time of that page query. This is not a live guarantee; status may change immediately, and disabled/demoted assignees remain assigned until an administrator clears or changes them.

`GET /api/v1/secure/investigations/{id}` returns tenant-scoped case detail and query-time assignee eligibility, auditing the case read. List accepts optional `status` (`open`/`closed`) and `assignee_id` filters in addition to `after`; preserve filters when following a cursor. Pages are not a snapshot, and filtering by another tenant user does not expose that user.

Analysts/admins may add an unverified text note to an open case with `POST /api/v1/secure/investigations/{id}/notes` and a `body` of up to 4000 characters. Authorized readers may list chronological notes with `GET` on that path and pass `next_cursor` as `after`. Notes have actor and timestamp; case history records the note ID and security audit records case and note targets atomically (events before this feature are not backfilled). Notes cannot be edited or deleted through the API, but database tamper protection is absent. Plain text must be escaped when rendered, and notes are not verified facts. Pagination is not a snapshot.

`GET /api/v1/secure/investigations/{case_id}/notes/{note_id}` returns a single tenant/case-scoped note and audits both targets; missing, foreign or mismatched IDs return 404. The response remains an unverified analyst assertion.

Administrator audit history accepts optional `investigation_id` and `event_type` filters (supported audit enum values); retain the same filters when following `next_cursor` as `before`. The cursor must belong to that tenant and filter scope; mismatches return 404. A foreign case filter yields no records, not a disclosure of existence. Access is audited, but historical case/note targets are not backfilled, and audit is not tamper-resistant.

Analysts/admins may update an open case via `PATCH /api/v1/secure/investigations/{id}` with `title`, `description` and `expected_version`. A locked PostgreSQL transaction checks tenant, role, open status and version; stale or closed cases return 409, foreign cases 404. Previous and current text are saved in case history and an update audit event commits atomically. History is not tamper-resistant or automatically redacted; safely escape it in any future UI.

Investigation list `after` must identify a case in the caller tenant that currently matches supplied status/assignee filters, otherwise 404. A changed status or assignment can invalidate an earlier cursor. This is an unsigned UUID anchor, not a filter-bound token or a consistent snapshot; reuse original filters and restart if necessary.

Case entity-link and evidence-link `after` cursors must identify an existing link within the same tenant and case, otherwise 404. Unlinking a cursor anchor invalidates it; restart pagination. These are UUID anchors, not snapshot cursors.

Entity list cursors require an existing entity in the tenant; entity evidence-list cursors require an existing evidence reference for that same entity and tenant. Invalid anchors return 404; deletions can invalidate cursors and pagination is not snapshot-consistent.

`POST /api/v1/secure/users/{id}/revoke-sessions` lets a tenant administrator revoke another same-tenant user’s existing unrevoked sessions and records a targeted audit event atomically. Self and cross-tenant targets are denied; count includes expired unrevoked sessions. This does not disable the account, change its password or stop future logins. For suspected credential compromise, session revocation alone is insufficient. PostgreSQL target-user locking serializes with session issuance; SQLite does not provide that guarantee.

`POST /api/v1/secure/password` requires a valid session plus `current_password` and `new_password` (12–1024 characters). Successful change revokes all the account’s existing sessions, including the caller, and requires a new login; the current hash and session are rechecked under lock before commit. Five attempts per account per fixed 60-second window are permitted (including successful attempts); throttling returns 429. This is not forgotten-password recovery, MFA, breach or reuse checking. Failed current-password and throttled attempts following initial session verification are audited without credentials; attribution is preflight, not a locked authorization decision. Audit growth, ingress protection and actual TLS still require verification.

`GET /api/v1/secure/me` returns the bearer session’s current tenant ID, user ID, username and role after locked reauthentication; the read is audited and fails if audit cannot commit. It does not expose session tokens or hashes. This experimental route does not provide browser session management.

`GET /api/v1/secure/users` is administrator-only and returns up to 100 same-tenant users per page with ID, username, role and active state, without password hashes or sessions. Continue with `after=next_cursor`; missing or foreign anchors return 404. The read is audited atomically; results are not a snapshot and anchor deletion can invalidate traversal.

`GET /api/v1/secure/sessions` lists only the caller’s session IDs, creation/expiry/revocation timestamps and current-session indicator; no token or digest is returned. It includes expired/revoked sessions pending cleanup; pass `next_cursor` as `after`, and a missing/foreign anchor returns 404. `DELETE /api/v1/secure/sessions/{id}` revokes one same-user session (including the caller), returning 404 for missing, foreign or already revoked IDs. Both operations are audited transactionally. Session-target audit UUIDs are snapshots without a session FK so cleanup does not delete or block audit; association is enforced by the route, not database FK, and historical events have no backfill. Pagination is not a snapshot.

`GET /api/v1/secure/entities/{id}` returns the same tenant-scoped public metadata projection as the entity list, with an unverified-data notice and targeted read audit. Cross-tenant and missing IDs return 404; internal properties are not returned. Metadata, provenance and evidence references remain incomplete and unverified.

`GET /api/v1/secure/entities` accepts an optional `kind` from the supported entity kinds. Continue with the same filter and `after=next_cursor`; the anchor must still belong to the tenant and match the current filter or 404 results. This is an unsigned UUID anchor, not a consistent snapshot or cryptographically filter-bound token.

`GET /api/v1/secure/entities/{entity_id}/evidence/{evidence_id}` returns a same-tenant, same-entity reference with an explicit unverified notice; missing or mismatched IDs return 404. Reference creation and single-reference reads record entity and evidence audit targets atomically. Migration 0027 enforces the composite tenant/entity/reference relationship, does not backfill historical audit, and may prevent deletion of referenced metadata. No file or supplied digest is verified.

Case evidence link/unlink audit events include tenant-scoped case, entity and evidence targets. Administrator audit reads accept `evidence_id` alongside case/event filters; use the same filters for continuation. Historical events without evidence targets do not appear in evidence-filtered results. Cursors are not snapshots, and target FKs can prevent evidence-reference deletion.

`GET /api/v1/secure/investigations/{case_id}/evidence/{link_id}` returns a tenant/case-scoped unverified association and records a case/entity/evidence-targeted read audit. Missing or mismatched identifiers return 404; no file or hash is checked. Association reads are not a durable snapshot and a concurrent unlink may follow.

`GET /api/v1/secure/investigations/{case_id}/entities/{link_id}` returns a tenant/case-scoped unverified entity association with case/entity-targeted read audit. Missing or mismatched identifiers return 404; an association is not evidence of involvement and may later be unlinked.

Administrator audit accepts an optional `entity_id` alongside case, evidence and event filters. Tenant scope always applies, and a continuation anchor must match current filters. Events without entity targets (including historical events) are not returned by this filter; pagination is not a snapshot.

Administrator audit accepts `user_id` to filter target-user events, combinable with other filters. This is not an actor filter: events without a matching target are excluded. Foreign IDs yield no results, and pagination is not a snapshot.

Entity listing accepts `q` (2–100 characters after trimming) for a literal case-insensitive title substring search, optionally combined with `kind`. Wildcards are literal and continuation anchors must match the current filters. Search may scan tenant data; case behavior for non-ASCII depends on database collation and is not validated. Query strings may be logged by intermediaries; do not put sensitive values in URLs until logging policy is controlled. Pagination is not a snapshot.

Investigation list accepts `q` (2–100 characters after trimming) for a literal case-insensitive title substring, combined with status/assignee. A continuation anchor must still match current filters. This may scan tenant data, Unicode case handling depends on database collation, URLs may be logged by intermediaries, and pagination is not a snapshot.

### NVD internal import (experimental)
`connectors/nvd_import.py` imports one structurally validated adapter observation for the authenticated administrator's tenant. It is an internal Python function, **not a sync-start HTTP API**, and does not fetch or schedule records. The source-specific observation and provenance are unverified; it orders by caller-supplied collection time and does not fuse records with CISA. Live NVD access and provider policy are unverified.

### NVD observation read
`GET /api/v1/secure/sources/nvd/cves/{cve_id}` returns the tenant's latest imported source-specific observation to authenticated readers. A successful read is transactionally audited against its entity. Missing or cross-tenant records return 404 and malformed identifiers return 422; responses are no-store. Data and timestamps are unverified, not evidence of current provider availability. No endpoint fetches or synchronizes NVD.

### Internal NVD synchronization
`connectors/nvd_sync.py` coordinates an explicitly invoked single-CVE lookup; it is not an HTTP endpoint or scheduler. It records running, succeeded, not_found, failed, and abandoned attempts per tenant. Successful import and attempt completion are atomic. Operators may abandon a running attempt through internal functions; abandonment prevents late imports but does not stop a network call. A crash can leave a running attempt; SQLite lacks concurrency guarantees. Tests use mocked synthetic data only. Provider access/terms, deployment-wide rate controls and live compatibility are not verified.

### NVD status and recovery
Administrators can inspect the latest tenant attempt with `GET /api/v1/secure/sources/nvd/status` and abandon a running attempt with `POST /api/v1/secure/sources/nvd/attempts/{attempt_id}/abandon`. Both require the experimental authenticated HTTPS API and are audited; foreign/non-running attempts return 404. A null attempt or successful/not-found attempt is not proof of current source health or vulnerability safety. Abandoning prevents late import but does not cancel network I/O. No start-sync API or scheduler exists.

### Interactive NVD CLI
From `apps/api`, an operator can run `python -m app.connectors.nvd_cli CVE-YYYY-NNNN --confirm-live-fetch` after setting `DATABASE_URL` for PostgreSQL and obtaining an administrator session. It requires a terminal and prompts for the token; it never accepts a token or endpoint URL as an argument. This triggers a real request to the fixed NVD endpoint, so do not run without authorization and verification of provider terms/rate policy. Tests use synthetic data and a simulated TTY only; live compatibility and actual terminal behavior are unverified. There is no scheduler, deployment-wide rate limiter or hard cancellation deadline.
