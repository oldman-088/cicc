# P2-01 experimental relationship API and host proposal

**Status:** real standalone ASGI routes and opt-in PostgreSQL implementation tested against an isolated local server. Not mounted or invoked through Agent 1's actual host; not approved for frontend or production. Legacy `ThreatIntelligenceAPI` is a separate simulated dispatcher, not this API. All current request data is constrained to `EXPERIMENTAL_DEMO_DATA_ONLY`.

## Host boundary and security
- Router: `apps.threat_intelligence.relationship_api.router`; standalone test app: `apps.threat_intelligence.api:app`. Proposed prefix `/api/v1/threat-intelligence`; no change to any shared host file. Host must override `get_principal` to verify authentication and construct `Principal(subject, tenant_id, permissions)` solely from trusted server-side identity and authorization. Default is 503; caller-provided tenant IDs/headers are never used. `threat:read` / `threat:write` permissions are required; missing permission is 403. Actual host identity binding is pending.
- Inject `PostgresRelationshipStore(engine)` in `app.state.relationship_store`; it never creates tables or manages engine lifecycle. The standalone app does not auto-configure storage. `InMemoryRelationshipStore` remains a volatile isolated test adapter. The host must inject `app.state.relationship_audit` callable for metadata-only attempts; missing/failing hook yields 503 before any store operation. It is not a durable security audit sink.
- `PostgresRelationshipStore(engine)` now defaults to `enforce_rls=True`: each transaction rejects a superuser/BYPASSRLS current role, checks that all four tables have RLS enabled and forced, rejects a pre-existing nonempty tenant setting on a pooled session, and binds a server-derived tenant using transaction-local `set_config('cicc.tenant_id', ..., true)`. `enforce_rls=False` is for the isolated legacy tests only. Each operation also applies tenant predicates and composite foreign keys. Proposed FORCE RLS policies and their rollback are in `schema/p2_01_rls_proposal.sql` and `schema/p2_01_rls_rollback_proposal.sql`; both were exercised only on a disposable local database with a restricted role. No shared migration was applied.
- **RLS security limitation:** the custom PostgreSQL setting is not authenticated: any party with arbitrary SQL access under the application role can set it to another tenant. It prevents accidental missing tenant filters only within a trusted app/connection boundary; it does not independently protect against SQL injection, stolen DB credentials or a malicious DB role. The checks verify RLS flags and current role attributes, not policy definitions, role memberships or grants. Superusers/BYPASSRLS bypass policies; role switching and mutable search paths must be prevented by host role policy. Owner review must approve the trust model, restrict role membership, schema/search-path privileges and direct SQL access, and verify policy/grant definitions and connection-pool behavior. This is not verified production tenant isolation.
- PostgreSQL successfully committed operations create a transactional audit row containing actor, tenant, operation, resource UUID when applicable, timestamp, outcome and server-generated correlation UUID. Write/idempotency row and audit row commit or roll back together. Successful reads and not-found reads also insert audit rows, making them database writes. The correlation UUID is in `X-Correlation-ID` for successful responses and explicit 404/409/graph-limit errors. Provenance is retained in the referenced relationship, not copied into audit; no request body, evidence, credential or free-text provenance is logged. The callback receives only subject, tenant and action. Denied/unauthenticated/validation failures, database failures, and graph-limit errors are not persisted by the DB audit; host must supply an independent security audit for them. No audit is retained if the database transaction itself fails. Missing/failed DB audit fails the operation with generic 500 and rolls back; fail-closed. In-memory audit is not durable or transactionally guaranteed.
- Standalone app sanitizes validation and unexpected exception responses. The host must install equivalent handlers and ensure server logs do not expose secrets. Enforce DB statement timeouts, connection limits, rate limits and payload limits at the host. No domain health/readiness API exists yet.

## HTTP routes
All require host identity and configured store/audit; DTOs are defined by `relationship_api.py` and exposed via standalone `/openapi.json`.

| Method/path (under prefix above) | Scope | Semantics |
| --- | --- | --- |
| POST `/relationships` | threat:write | `RelationshipCreate`, required 1–128 character `Idempotency-Key` (`A-Z a-z 0-9 . _ : -`). 201 created; 200 exact replay or identical payload with another key; 409 same tenant/key with different normalized payload. Distinct evidence/provenance is preserved as separate observations. |
| GET `/relationships` | threat:read | Paired optional `entity_id`/`entity_type`, optional `relationship_type`, `limit` 1–500 default 100, `offset` 0–100000; `items,total,offset,limit,has_more`. Empty returns 200. |
| GET `/relationships/{relationship_id}` | threat:read | UUID; 200 record or 404, including another tenant's record. |
| POST `/relationship-analysis/traverse` | threat:read | Entity ID/type, `max_depth` 0–8 default 3, optional relationship enum list, limit/offset; 404 for missing indexed entity. BFS is undirected, edge-unique, cycle-safe and filter constrains traversal. Returns full stored relationships including evidence, confidence and provenance; items carry depth. Empty filter means no edges. PostgreSQL uses indexed frontier queries and a repeatable-read snapshot; exceeding configured 10,000 edges/rows scanned per frontier returns 422 rather than partial data. |

Creation validates bounded nonempty references/provenance, enums and up to 100 evidence objects with timezone-aware timestamps. Confirmed assertions require evidence and cannot have inferred confidence. This validates shape only, not truth. No confidence calculation or freshness estimate is provided. Entity identity is `(tenant, type, id)`; names are observation metadata. Ordering uses database insertion sequence for a fixed snapshot (in-memory uses insertion order); offset pagination can shift with new records between requests. Conflicting observations remain separate; conflict resolution is not implemented. Standalone response errors: 401 if supplied host auth rejects credentials, 403, 404, 409, 422, 503 as above, or generic 500. Host behavior needs agreement.

## PostgreSQL and migration proposal
`apps/threat_intelligence/relationship_storage.py` defines PostgreSQL SQLAlchemy Core tables, tenant-aware entity/relationship/idempotency constraints, adjacency/type indexes and transactional audit. A per-tenant PostgreSQL transaction advisory lock serializes creation across workers; database uniqueness and foreign keys enforce identity and idempotency. Graph reads use indexed frontier queries. This is a reviewed-domain proposal, not an approved shared schema. No schema is created at app startup.

`apps/threat_intelligence/schema/p2_01_postgres_proposal.sql` is an independently owned, additive forward migration proposal tested on a fresh isolated database. Apply the separate RLS proposal after it only with owner approval; its separate rollback disables RLS and is security-sensitive, not a safe default. Both RLS forward and rollback were tested on an isolated local database. Agent 1/owner must review schema placement, role grants, versioned migration integration, tenant policy, audit retention and operational impact before any shared deployment. Rollback **requires owner approval and a verified backup**: stop writers, preserve/export relationship, identity, idempotency and audit data, then remove these four tables in reverse dependency order (idempotency, relationship, entity, audit) via the host migration system. Dropping tables destroys data and was not executed on shared infrastructure. Audit retention/legal requirements may prohibit deletion. No shared migrations were modified.

## Reproduction and coordination
Fresh test environment: `python3 -m venv /home/user/.venv-cicc-pg && /home/user/.venv-cicc-pg/bin/pip install -r requirements-threat-intelligence-test.txt`. Run `CICC_TEST_PG_EMBEDDED=1 /home/user/.venv-cicc-pg/bin/python -m pytest -q --disable-warnings`. Embedded pgserver starts a fresh local PostgreSQL cluster in pytest's temporary directory and applies the exact proposed SQL, never an external configured database. Without the opt-in flag, PostgreSQL tests skip. These tests exercise real ASGI requests and local PostgreSQL, not Agent 1's host or live providers. The RLS tests use a local non-superuser, non-BYPASSRLS role with SELECT/INSERT privileges and exercise pool reset and poisoned-session rejection, cross-tenant SELECT/INSERT/UPDATE/DELETE/traversal/audit, denied role changes and rollback. UPDATE/DELETE are not granted to the normal test role; separate isolated tests temporarily grant them to verify RLS filtering and WITH CHECK.

Agent 1: review principal/tenant, gateway mapping, schema, transaction/audit and routing contracts; no agreement or host mount is implied. The current PR #4 adapter invokes the legacy demo, and its response timestamp / 1.0 value do not establish source freshness or intelligence confidence. Agent 4: no browser binding to these routes; preserve approved create-only BFF write boundary `POST /api/v1/coordination/tasks`. Frontend DTOs require approved gateway/host decisions first.
