# Experimental P2-01 relationship API and handoff

Status: **independent application tests only; not approved or mounted in the Agent 1 host; not frontend-ready**. The legacy `ThreatIntelligenceAPI` in `api.py` is a separate in-process demo and must not be used as the real relationship API. Its simulated data is always marked `EXPERIMENTAL_DEMO_DATA_ONLY`. The Agent 1 adapter inspected at PR #4 head `752dc99ececef934fef2d699aae571502639bc1f` invokes that legacy dispatcher, not these routes; its timestamps are response-generation times, not source freshness, and its `1.0` is not an intelligence confidence score.

## Entry point and host obligations
- Import `apps.threat_intelligence.relationship_api.router`; include it with FastAPI `include_router(router)`. `apps.threat_intelligence.api:app` includes this router for isolated tests. No changes to Agent 1's host were made.
- Default `get_principal` fails with 503; the host must override the dependency with credential verification and a `Principal(subject, tenant_id, permissions)` constructed entirely from trusted server-side identity and policy, not request payloads or arbitrary headers. The only permissions currently checked are `threat:read` and `threat:write`. The app does not implement login or token verification.
- Host must provide `app.state.relationship_store` and `app.state.relationship_audit`. `InMemoryRelationshipStore` is an explicitly injected, single-process, volatile test implementation; do not use it for production or multi-worker deployment. Tenant scope is a dictionary keyed from the trusted principal, protected by an in-process lock. The host must supply a reviewed persistent, tenant-aware adapter implementing the same store contract, or replace the dependency; the present code relies on the in-memory interface and lock, not a general database abstraction.
- The audit callable is invoked synchronously for authorized attempts with `{subject, tenant_id, action}` only, before operations. Exceptions fail closed with 503. It does not record outcomes, denied/unauthenticated requests, correlation IDs, or provide durable/transactional audit guarantees. Host must provide those separately. Host must install safe validation and exception handlers analogous to the standalone app and avoid logging raw input or secrets. Body limits, abuse/rate controls, distributed consistency and failure handling belong to the host.
- No health/readiness endpoints are provided here; an unconfigured principal, store or audit returns 503. This is not a complete readiness check and should not be advertised as one. No timeouts are implemented by this synchronous in-memory module; the host/gateway must specify and enforce them.

## Routes (prefix `/api/v1/threat-intelligence`)
All requests require the trusted principal and configured storage/audit. Data models are generated from `relationship_api.py` in OpenAPI (`/openapi.json` on the standalone test app).

| Method/path | Permission | Contract |
| --- | --- | --- |
| POST `/relationships` | threat:write | `RelationshipCreate` JSON, required `Idempotency-Key` header (1–128 alphanumeric/`._:-` chars); 201 created; 200 exact replay/duplicate; 409 same tenant/key with different normalized payload. Exact payload duplicates, including provenance and evidence, are deduplicated per tenant; different observations are retained. |
| GET `/relationships` | threat:read | Optional paired `entity_id` and `entity_type`, optional enum `relationship_type`, `limit` 1–500 (default 100), `offset` 0–100000. Returns `RelationshipPage` (`items,total,limit,offset,has_more`); empty is 200. |
| GET `/relationships/{relationship_id}` | threat:read | UUID; 200 record or 404, including records in another tenant. |
| POST `/relationship-analysis/traverse` | threat:read | `TraversalInput`: entity ID/type, `max_depth` 0–8 default 3, optional relationship-type enum list, offset/limit as above. 404 if no entity in this tenant's relationship index. Returns `TraversalPage` with edge depth and complete stored relationship/evidence per item, total and visited count. Traverses undirected graph breadth-first, one result per stored edge; filtered edges are not traversed. Empty filter means no edges. |

Creation requires nonempty bounded entity IDs/types and provenance, enum type/confidence, a boolean confirmation flag, and up to 100 evidence entries with source, description, provenance, timezone-aware collection timestamp and confidence. A confirmed assertion requires evidence and cannot be marked inferred; this is a syntactic check, not verification of truth. `CONFIRMED` confidence requires `confirmed=true`. `experimental_label` on records, entity references and evidence is currently restricted to `EXPERIMENTAL_DEMO_DATA_ONLY`; this surface is therefore explicitly experimental, not a live provider API. Each response preserves stored provenance, evidence, confidence, timestamps and label. No freshness or source reliability is calculated. Entity identity is the tuple `(type,id)`; names are observation metadata, not a canonical entity registry. Order is insertion-based, deterministic for a fixed store state; offset pagination has no snapshot guarantee under concurrent writes. Traversal materializes the reachable graph before pagination; depth is bounded but graph size is not. No persistence across restart is supported.

Standalone app error responses: 401 when the injected auth dependency rejects credentials, 403 for missing permission, 404 missing item/entity, 409 idempotency conflict, 422 malformed input, 503 missing dependency/audit failure, and generic 500 on unexpected errors. Host-specific handlers may differ unless coordinated. The standalone validation handler suppresses input details; host must install equivalent redaction. No response should be interpreted as source verification. Conflicting observations are stored as separate records; conflict resolution is not implemented.
