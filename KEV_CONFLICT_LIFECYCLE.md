# KEV conflict lifecycle — M49 proposal and isolated implementation

## Inspection implemented; no resolution implemented
`persist_catalog` serializes a trusted worker per origin, verifies incoming exact bytes/digests, revalidates the previous snapshot, and quarantines a semantically different catalog with the **same** release timestamp. Previous snapshot remains active; `checked_at` is not advanced; candidate and previous raw bytes are retained. Repeated same conflict is idempotent; CLI returns nonzero. No winner is chosen. Earlier release input is rejected, not quarantined. Source release, collection time and conflict first-observed time are distinct; `observed_at` is caller/worker supplied, not independently trusted or monotonic.

`inspect_conflict(engine, origin=..., conflict_id=...)` is a trusted-operator, read-only, repeatable-read interface: it verifies and returns both `CollectedCatalog` objects (exact raw bytes obtainable through `verify_source_bytes`), SHA-256 and Git blob hashes, both collection times, release time, first observation, snapshot ID and sorted added/removed/changed CVE IDs and changed catalog metadata fields. It rejects missing, corrupt or inconsistent evidence. It exposes potentially untrusted provider data and is not a public or tenant endpoint. SHA-256/Git blob checking proves consistency only, not publisher authenticity or privileged-admin resistance. `load_conflict_candidate` and `load_snapshot` independently support verified replay. Health count includes all retained conflicts; there is no resolution state, so it must not be interpreted as only newly actionable incidents.

## P2-05 exact proposal and compatibility
`schema/p2_05_kev_conflict_proposal.sql` creates `ti_kev.source_conflict` with identity primary key, origin, previous snapshot ID, candidate SHA-256 and first-observed timestamp; composite foreign keys refer to existing snapshot `(id,origin)` and source blob `(origin,content_sha256)`, and a unique `(origin,previous_snapshot_id,candidate_content_sha256)` deduplicates retries. PUBLIC has no table or sequence privileges. It adds no tenant table, host route, role or audit table. Existing P2-02–04 data are unchanged. The updated worker can process normal non-conflicting collection without referencing P2-05 but **conflict writes and the updated health reader require P2-05**; downgrade/old readers do not surface quarantines. Therefore deploy the compatible schema and reviewed grants before the new worker/health reader. Older workers do not quarantine conflicts and must not run concurrently during cutover. Old snapshots without original bytes/metadata fail closed on new promotion unless exact-byte backfilled by an unchanged fetch; plan capacity and recovery for this.

Separate role proposal: schema owner owns objects and migration, not runtime; collection worker gets schema USAGE, SELECT/INSERT on necessary snapshot/revision/membership/metadata/blob/conflict tables, USAGE on needed identity sequences and UPDATE only `snapshot.checked_at`; no UPDATE/DELETE on conflict/blob/revision. Operator health/inspection gets schema USAGE and SELECT on the necessary tables, no writes or sequence access. Grant design must be reviewed against actual deployment and existing P2-02–04 objects, role inheritance and connection pooling; do not grant broad runtime privileges to tenant application identities. These public-feed records are global, not tenant-owned, and do not implement tenant isolation. Tenant-scoped correlation requires the separately approved verified principal/pool and controlled relationship access; inspection must be host-operator restricted. Database owners/superusers can rewrite this data and audit; hashes are not independent trust anchors.

Apply 02→03→04→05 only after owner approval, backup, grant review and isolated rehearsal. Stop older workers during cutover. On rollback, stop worker/health consumers, export and verify both conflict streams plus conflict metadata and audit, and obtain explicit destructive rollback approval; 05→04→03→02 is reverse dependency order. P2-05 rollback drops conflict references/metadata and the following P2-04 rollback drops blobs, so both lose evidence without verified backup. No shared migration, alert routing or scheduler has been applied.

## Resolution interface and audit requirements — design only
Proposed host-owned operation: `request_conflict_resolution(conflict_id, expected_previous_sha256, expected_candidate_sha256, disposition, rationale, idempotency_key)` with a verified server-derived actor and authorized operator permission. The request must never trust tenant, actor or role in caller content. Proposed dispositions should initially support `acknowledge_unresolved` and `request_source_recheck`; a selection/promotion action requires a separately approved source-authority and recovery policy and is **not implemented**. No disposition deletes or mutates either original blob, snapshot, conflict, or prior audit. Re-inspect/validate both hashes and verify the expected IDs in the same transaction, lock the conflict, enforce idempotency and append a separately provisioned resolution event; reject stale IDs or altered evidence. Preserve observation and decision times, origin, conflict/snapshot IDs, both digests, verified actor, controlled disposition, bounded rationale/reference and correlation ID. Audit and state change must commit or roll back together, with DB-derived identity and narrowly granted insert-only mechanisms; rejected/unauthorized attempts require a separately trusted security sink. Audit must not include raw blobs, secrets, tokens or sensitive request data. Privileged admins can bypass ordinary SQL grants; stronger guarantees require independently controlled external retention. Concurrent/repeated requests and retries require explicit tests before approval. This proposal makes no claim of an already-existing resolution API, schema, audit mechanism or approval.
