# Controlled relationship writes and database audit — isolated implementation

`TrustedWritePostgresRelationshipStore` in `apps/threat_intelligence.relationship_storage` is an **experimental controlled create/get adapter**, not the default store and not mounted in the Agent 1 host. It can be injected into the existing standalone FastAPI app. It supports a single-record get via `p2_01_trusted_get_proposal.sql`, which derives identity, records success/not-found audit and returns a DB-generated correlation ID in the same transaction. It intentionally returns HTTP 503 for list and traversal until audited entry points exist. The existing full-featured store and its behavior remain available separately.

## Implemented boundary
`schema/p2_01_trusted_write_proposal.sql` adds a protected login-to-actor mapping and a narrowly scoped SECURITY DEFINER `ti_security.trusted_create_relationship(key, record)`. It derives tenant and actor from protected mappings keyed by PostgreSQL `session_user`; derives audit event UUID, `relationship.create` event type, outcome, correlation UUID and occurrence time inside PostgreSQL; and writes the relationship, idempotency record and audit row in one transaction. No tenant, actor, audit type, timestamp, outcome or correlation is accepted as an audit argument. An invalid audit insert aborts the relationship and idempotency writes. The API returns the DB-generated correlation ID. The adapter verifies its trusted host tenant/actor match the DB identity, including values returned by the DB write statement before commit, so an intervening identity-map change fails closed. Retries and duplicates use a DB-computed digest of canonical JSONB after excluding generated record/evidence identifiers and record timestamps; evidence content, source and collection time remain in the digest. This fingerprint differs from the full-featured legacy store; **do not mix the two stores against the same live dataset without an agreed migration/idempotency plan**.

The tested runtime DB role has EXECUTE on required identity/create/get functions and **no direct SELECT, INSERT, UPDATE or DELETE** on relationship, identity or audit tables and no mapping/DDL/other-tenant role privileges. The protected mappings and functions must be owned by a trusted, restricted NOLOGIN owner; role membership, grants, schema privileges, search path and principal-per-login pool selection must be deployed and reviewed by the host/database owner. Tests run with an isolated administrator owning the function; that is not a production grant template. SQL functions use fixed `pg_catalog` search paths and schema-qualified table references. The login-to-actor mapping identifies the PostgreSQL login's provisioned actor; it is an end-user identity only if the real host securely provisions and binds one actor per login. The owner must separately grant restricted runtime roles USAGE/EXECUTE.

The function checks basic structure, demo labels, identifiers and confidence/evidence consistency, but it is not a complete SQL-side equivalent of Pydantic request validation. A tenant principal with arbitrary SQL and function EXECUTE can initiate real creates within its own tenant, invent source claims/record metadata, or cause repeated legitimate audited operations; this is not a substitute for application authorization or data verification. It cannot directly insert fake audit actors, times or event types under the tested grants, but a privileged database owner, superuser, BYPASSRLS, compromised mapping/function, unsafe privileges, or leaked other-tenant credential can subvert it. Audit is transactionally consistent and protected against tested runtime-role direct mutation; it is **not WORM/externally immutable**, independent of database administrators, or comprehensive: denied/failed operations, list/traversal, unauthorized direct SQL attempts, and host security events require a separate trusted security audit. The DB-generated correlation is not yet linked to Agent 1 task/trace; approved host mapping is still required.

## Migration, rollback and tests
Apply the five independently owned SQL proposals only to an authorized test DB and after role-bound RLS (`p2_01_postgres_proposal.sql`, `p2_01_rls_proposal.sql`, `p2_01_role_bound_rls_proposal.sql`, then `p2_01_trusted_write_proposal.sql` and `p2_01_trusted_get_proposal.sql`). `p2_01_trusted_get_rollback_proposal.sql` and `p2_01_trusted_write_rollback_proposal.sql` withdraw their respective functions but retain identity mappings; it requires owner approval and a maintenance/recovery plan. Recreating the function requires regranting EXECUTE. Neither script was applied to shared infrastructure.

`CICC_TEST_PG_EMBEDDED=1 /home/user/.venv-cicc-pg/bin/python -m pytest -q apps/threat_intelligence/tests/test_trusted_write.py --disable-warnings` uses a disposable real PostgreSQL server and actual standalone ASGI calls; tests successful/duplicate/conflict writes, concurrency, DB actor/time/correlation, direct SQL data read and audit forgery/mutation denial, cross-tenant get, audit failure, mapping-change races, and rollback/reapply for both functions. This does not test the actual Agent 1 gateway, actual end-user authentication or production deployment.
