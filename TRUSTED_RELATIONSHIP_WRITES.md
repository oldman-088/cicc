# Controlled PostgreSQL relationship create and reads — isolated implementation

`TrustedWritePostgresRelationshipStore` is an experimental injectable adapter supporting create, single-record get, tenant-scoped list/filter/offset pagination, and breadth-first traversal. Database functions derive tenant and actor from protected mappings keyed by `session_user`, derive audit event UUID/type/outcome/time and correlation in PostgreSQL, and atomically write the operation's audit with the operation. API `threat:read` / `threat:write` authorization applies to all four routes. The DB runtime must receive EXECUTE **only for its granted operations**; one login with broad function grants can bypass application-only permission checks through SQL. Tests demonstrate a read-only login denied create and ungranted traversal. None is mounted in the real Agent 1 host.

The list query filters and counts only the authenticated tenant, orders by immutable insertion sequence, and computes count and page from one SQL statement. Traversal sees a repeatable-read snapshot in the adapter, visits `(entity_type, entity_id)` pairs breadth-first, emits edges in sequence order at each depth, supports type filters and offset/limit, and returns tenant-local counts only. It is capped at 1,000 scanned edges per frontier and 1,000 unique edges per request; a cap breach returns 422, no partial data and an audited `limit_exceeded` outcome. Pagination is offset-based, not a cross-request snapshot token; privileged changes or concurrent additions between page requests can affect a multi-page export. Set and monitor appropriate database-side statement timeouts and resource quotas before deployment; the cap is not a complete workload-control mechanism.

## Security boundary and remaining risks
In the tested configuration, runtime DB logins cannot SELECT, INSERT, UPDATE or DELETE underlying relationship, identity or audit tables and have only operation-specific EXECUTE permissions. Fixed-search-path SECURITY DEFINER functions explicitly filter by tenant and generate audit fields, rather than accepting caller tenant, actor, correlation, event type, outcome or timestamp. Audited reads, writes, idempotency and audit insertion share a transaction; audit or response-record validation failure aborts the transaction. A returned DB correlation ID is not caller-controlled. Controlled not-found and traversal-cap responses are audited without exposing other tenants' existence. An isolated test demonstrates reused backend connections with a malicious session GUC still use the authenticated login's tenant; different actors/tenants must have separately authenticated server logins and pools.

Production prerequisites: protected mappings and function ownership by a reviewed NOLOGIN owner; exact schema/function EXECUTE grants matching host permissions; no direct table grants, role memberships or writable function/search-path objects; protected credential provisioning and pool routing; reviewed RLS policies, timeout/quota and host audit. PostgreSQL logins bind to provisioned actors, not automatically authenticated humans. The host must verify the human/session and route to the matching actor/tenant login and only grant permitted operations. With repeatable-read snapshots a mapping change may not take effect for an already-running transaction; revoke sessions/credentials according to the host's incident procedure. Database administrators, owners, superusers, BYPASSRLS, compromised mappings/functions, leaked login credentials and unrestricted SQL grants can defeat the boundary. Tests used an isolated administrator as function owner; that is **not** a production grant template.

Authorized or compromised logins can invoke granted functions and submit fabricated own-tenant intelligence. Create performs structural checks, not full SQL-side Pydantic-equivalent validation or source verification. Audit is transactionally consistent and protected from tested runtime-role direct modification, but not WORM or independent of administrators. Authentication/authorization denial, malformed input, failed DB operations and direct SQL denial need a separate host security-event sink. The database-generated correlation is not linked to Agent 1 task/trace yet. The controlled DB fingerprint differs from the legacy full store's Python fingerprint; do not mix them in one dataset without an approved compatibility/migration plan. Privileged direct writes can create invalid records; the adapter validates output and aborts the read transaction on invalid data.

## Proposals and rollback
For an authorized disposable database apply, in order: `p2_01_postgres_proposal.sql`, `p2_01_rls_proposal.sql`, `p2_01_role_bound_rls_proposal.sql`, `p2_01_trusted_write_proposal.sql`, `p2_01_trusted_get_proposal.sql`, `p2_01_trusted_query_proposal.sql`. Provision reviewed owners, role/login mappings and per-operation grants separately. `p2_01_trusted_query_rollback_proposal.sql`, `p2_01_trusted_get_rollback_proposal.sql`, and `p2_01_trusted_write_rollback_proposal.sql` withdraw their respective functions; they leave mappings/data intact and require regranting EXECUTE on reapply. Tested only on disposable PostgreSQL; no shared migration/role applied.
