`apps.threat_intelligence.relationship_api.router` is included by `api.py:app`; `host_adapter.create_host_application()` creates a separate subapplication containing it. **Neither is mounted in Agent 1's actual host.** All paths below are router paths before any owner-approved host mount prefix; host prefix may change them. | Method/path | Required scope | Input → output and semantics |
|---|---|---|
| `POST /api/v1/threat-intelligence/relationships` | `threat:write` | `RelationshipCreate` and `Idempotency-Key` 1–128 chars matching `[A-Za-z0-9._:-]+` → `RelationshipRecord`; 201 created, 200 replay/equivalent payload, 409 key reused with different normalized payload. |
| `GET /api/v1/threat-intelligence/relationships` | `threat:read` | Optional **paired** `entity_id`+`entity_type`, optional `relationship_type`, `limit` 1–500 default 100, `offset` 0–100000 → `RelationshipPage {items,total,offset,limit,has_more}`. | `GET /api/v1/threat-intelligence/relationships/{relationship_id}` | `threat:read` | UUID → `RelationshipRecord`; missing or other tenant returns 404 under controlled implementation. |
| `POST /api/v1/threat-intelligence/relationship-analysis/traverse` | `threat:read` | `TraversalInput {entity_id,entity_type,max_depth:0..8=3,relationship_types?:list≤15,limit:1..500=100,offset:0..100000=0}` → `TraversalPage {entity_id,entity_type,max_depth,visited_entities,items:[{depth,relationship}],total,offset,limit,has_more,experimental_label}`; tenant-local missing entity 404. |

`RelationshipCreate` requires `source_entity` and `target_entity` (`entity_id`, `entity_type`, optional `name`, experiment label), `relationship_type`, declared `confidence`, `provenance`; optional `evidence` (≤100 objects with `source`, timezone-aware `timestamp`, `description` ≤4096, declared confidence, provenance, label), `confirmed` and label. Entity/text/provenance input fields are stripped nonempty ≤256 chars. Enums in `relationship_analysis.py`: type `ATTRIBUTED_TO`, `USES`, `TARGETS`, `INDICATES`, `ASSOCIATED_WITH`, `EXPLOITS`, `AFFECTS`, `OBSERVED_IN`, `DERIVED_FROM`, `CORROBORATES`, `CONTRADICTS`, `CONTAINS`, `DEPENDS_ON`, `BELONGS_TO`, `RELATED_TO`; confidence `LOW`, `MEDIUM`, `HIGH`, `CONFIRMED`, `INFERRED`. A confirmed relationship needs evidence and cannot use INFERRED; CONFIRMED confidence requires `confirmed=true`. Extra request fields rejected; callers cannot set tenant. Responses add UUIDs/times and record-level optional temporal/conflict fields. Shape validation does not prove claims.

The default principal dependency fails with 503; the actual host must authenticate and supply `Principal(subject,tenant_id,permissions)` from trusted server-side identity, never a body/header/transaction GUC. Missing permission 403; host auth may return 401; missing dependency/audit/trace 503; invalid input 422; conflict 409; unexpected storage failure sanitized 500. `X-Correlation-ID` is DB correlation, not client authority. Host adapter catches/sanitizes validation/internal errors and attempts metadata-only security events; host must audit gateway rejections/direct SQL itself. Trace or post-commit audit callback can fail **after commit**, so a 503 is not proof of rollback; retry create with the same idempotency key and reconcile late callbacks.

The trusted DB graph traversal is bounded at 1,000 edges and 4 MiB returned-record JSON text; the alternative generic PG store has a configurable default 10,000 scanned/returned graph edge limit. This is not a wire-body limit. No application HTTP rate limiter, statement timeout, common wire-size cap or cross-worker limiter is implemented; Agent 1 must enforce approved limits. Its observed 16 KiB host body cap may conflict with this API. The legacy `ThreatIntelligenceAPI._mounted_endpoints` dictionary in `api.py` is a **simulated dispatcher**, not real HTTP routes; never expose it as the approved gateway. VI quality/SBOM/KEV/conflict candidates in `docs/vi_candidate_contracts/` have no actual HTTP routes. ## 5. Database, roles and audit

`relationship_storage.py` SQLAlchemy Core models correspond to proposed `schema/p2_01_postgres_proposal.sql`: `ti_relationship_entity` (tenant/type/id key); `ti_relationship_record` (tenant, UUID, sequence, source/target FKs, relationship type, canonical fingerprint, JSONB record and indexes); `ti_relationship_idempotency` (tenant/key/fingerprint/relationship FK); `ti_relationship_audit` (UUID, tenant, actor, operation, resource UUID, outcome, correlation UUID and UTC time). DB advisory locking + unique constraints serialize tenant create/idempotency. Evidence/provenance remain in record JSONB, not audit. Successful and not-found reads write transactional audit; denied gateway/validation/direct-SQL failures need host security audit.

All files in `apps/threat_intelligence/schema/` are **proposals**, not installed shared migrations. In isolated DB, apply base P2-01 then RLS, role-bound RLS, trusted write, trusted get, trusted query proposals in that order when testing the controlled path (see fixtures in `test_trusted_write.py` and `test_host_adapter.py` for exact grants). The controlled SQL exposes `ti_security.authenticated_tenant()`, `authenticated_actor()` and `trusted_create_relationship`, `trusted_get_relationship`, `trusted_list_relationships`, `trusted_traverse_relationships`, with protected `tenant_role_map` and `login_actor_map`; actual roles, ownership and EXECUTE grants require DB/security approval. P2-02→P2-05 propose `ti_kev.snapshot`, `revision`, `snapshot_entry`, `catalog_metadata`, `source_blob`, `source_conflict`; origin separates live-mirror and fixture streams. Forward and rollback proposal filenames and dependency order are in `CISA_KEV_COLLECTOR_CONTRACT.md`. **Do not run rollback on shared infrastructure**: data deletion/security downgrades require owner-approved backups, retention and recovery plan.

The earlier `cicc.tenant_id` custom-GUC RLS is not an authentication boundary: arbitrary SQL can change it. Role-bound local RLS uses protected PostgreSQL `session_user` mapping and separate login pools; host verification, mapping ownership, grants, pooler behavior and credentials remain unapproved. A role with own-tenant direct audit INSERT can forge its own audit. Controlled DB functions derive actor/tenant from protected maps and combine write/audit/rollback in isolated tests; administrator/superuser/BYPASSRLS or compromised owner/credentials defeat this model. DB functions do not fully reproduce API validation; never expose arbitrary callers. Controlled DB fingerprints differ from legacy Python fingerprints: do not mix stores in shared tables without an approved migration. Do not log request payloads, credentials or source bytes.
